## Exercise 1 — Store favorite websites using Strings

Objective: Use `SET`, `GET`, `MSET`, and `MGET` to create and retrieve URL mappings.

### Solution

python

```
# Store individual URL mappings.
client.set("lab1:url:uab", "https://www.uab.cat")
client.set("lab1:url:google", "https://www.google.com")
client.set("lab1:url:youtube", "https://www.youtube.com")

# Retrieve one mapping.
print("UAB:", client.get("lab1:url:uab"))

# Store multiple mappings in one command.
more_urls = {
    "lab1:url:github": "https://github.com",
    "lab1:url:wikipedia": "https://www.wikipedia.org",
    "lab1:url:stackoverflow": "https://stackoverflow.com"
}

client.mset(more_urls)

# Retrieve multiple mappings.
keys = list(more_urls.keys())
values = client.mget(keys)

for key, value in zip(keys, values):
    print(f"{key} -> {value}")
```

### Explanation

- `SET` creates or replaces a String value associated with a key.
- `GET` retrieves one value.
- `MSET` stores several key-value pairs in one command.
- `MGET` retrieves several values in the order of the requested keys.

Redis Strings are appropriate for simple URL mappings because each key identifies one stored value.

Exercise 1 is complete when the three individual mappings and the three mappings stored with `MSET` are retrieved correctly.

## Exercise 2 — Count stored URLs using `INCR`

Objective: Initialize a counter, add three URL mappings, increment the counter for every newly added mapping, and explain why `INCR` is safer than manually updating the value.

### Solution

python

```
# Reset the exercise's keys to make the example reproducible.
client.delete(
    "lab1:count",
    "lab1:url:example1",
    "lab1:url:python",
    "lab1:url:redis"
)

client.set("lab1:count", 0)

urls = {
    "lab1:url:example1": "https://example.com",
    "lab1:url:python": "https://www.python.org",
    "lab1:url:redis": "https://redis.io"
}

for key, url in urls.items():
    # NX means set only if the key does not already exist.
    created = client.set(key, url, nx=True)

    if created:
        client.incr("lab1:count")

print("Final URL counter:", client.get("lab1:count"))

assert int(client.get("lab1:count")) == 3
print("Counter verification passed.")
```

Expected output:

text

```
Final URL counter: 3
Counter verification passed.
```

### Why is `INCR` safer?

Redis executes `INCR` atomically. If two clients increment the same counter concurrently, Redis processes both increments rather than allowing one client's update to overwrite the other.

By contrast, a manual sequence such as `GET`, increment in Python, then `SET` can lose updates if multiple clients read the same initial value.

The `NX` condition makes the example safe to rerun without overwriting existing mappings or counting the same newly created key again. In a production URL-shortening service, mapping creation and counter updates may need to be combined in a transaction or Lua script if they must succeed or fail together.

## Exercise 7 — Combine votes and visits into a relevance ranking

Objective: Combine vote scores and visit scores, giving votes twice the weight of visits.

### Solution

python

```
votes_key = "lab1:ranking:votes"
visits_key = "lab1:ranking:visits"
relevance_key = "lab1:ranking:relevance"

client.zadd(votes_key, {
    "uab": 5,
    "google": 1,
    "bing": 10
})

client.zadd(visits_key, {
    "uab": 20,
    "google": 1234,
    "github": 30
})

# Relevance = (votes * 2) + visits.
client.zunionstore(
    relevance_key,
    {votes_key: 2, visits_key: 1},
    aggregate="SUM"
)

print("Relevance ranking, highest first:")
print(client.zrevrange(
    relevance_key, 0, -1, withscores=True
))
```

### Expected scores

| URL | Votes | Visits | Relevance |
| --- | --- | --- | --- |
| `uab` | 5 | 20 | 30 |
| `google` | 1 | 1234 | 1236 |
| `bing` | 10 | 0 | 20 |
| `github` | 0 | 30 | 30 |

The formula is:

$$
\text{relevance}(u)=2\cdot\text{votes}(u)+\text{visits}(u)
$$

The weights are applied to the respective input ZSETs. If a URL exists in only one input ZSET, the missing score is treated as zero.

Important interpretation: The result follows the assignment's specified formula. In a real recommender, the raw number of visits may dominate votes, so score normalization or a different weighting scheme might be needed.

## Exercise 8 — Redis Lists: wishlist, queue, stack, and visited URLs

Lists are ordered collections that permit duplicate values. They are suitable for histories and ordered workflows.

### Solution

python

```
wishlist_key = "lab1:user:0001:wishlist"
visited_key = "lab1:user:0001:visited"

client.delete(wishlist_key, visited_key)

# Store URLs in the wishlist.
client.rpush(wishlist_key, "google", "bing", "github")

print("Wishlist:", client.lrange(wishlist_key, 0, -1))
print("Wishlist length:", client.llen(wishlist_key))

# Move the rightmost wishlist item to the left of the visited List.
moved_url = client.rpoplpush(wishlist_key, visited_key)

print("Moved URL:", moved_url)
print("Remaining wishlist:", client.lrange(wishlist_key, 0, -1))
print("Visited URLs:", client.lrange(visited_key, 0, -1))

# Demonstrate a queue: insert on the left, remove on the right.
queue_key = "lab1:demo:queue"
client.delete(queue_key)
client.lpush(queue_key, "first", "second", "third")

print("Queue before removal:", client.lrange(queue_key, 0, -1))
print("Dequeued:", client.rpop(queue_key))

# Demonstrate a stack: insert and remove on the same end.
stack_key = "lab1:demo:stack"
client.delete(stack_key)
client.rpush(stack_key, "first", "second", "third")

print("Popped from stack:", client.rpop(stack_key))
print("Remaining stack:", client.lrange(stack_key, 0, -1))
```

### Explanation

- `RPUSH` inserts values at the right.
- `LPUSH` inserts values at the left.
- `LRANGE` retrieves a range of elements.
- `LLEN` returns the number of elements.
- `LPOP` and `RPOP` remove an element from the left and right, respectively.
- `RPOPLPUSH` atomically removes the rightmost element from a source List and inserts it at the left of a destination List.

The order of insertion and removal determines whether a List behaves like a queue or a stack. In this example, the wishlist and visited history are independent Lists, and `RPOPLPUSH` demonstrates moving a URL between them.

Note that `RPOPLPUSH` is deprecated in newer Redis versions in favor of `LMOVE`. The equivalent modern operation is:

python

```
client.lmove(wishlist_key, visited_key, "RIGHT", "LEFT")
```

Use one of these operations, not both, for the same movement.

# Part D — Deliverable 2: Top 10 most active users

## 2.1 Definition of user activity

For this lab, define activity as the total number of accepted URL posts and accepted votes:

$$
\text{activity}(u)=\text{posts}(u)+\text{votes}(u)
$$

Each new URL posted contributes one point, and each accepted vote contributes one point. A repeated vote for the same URL by the same user contributes no additional points.

This is a simple definition for the assignment. A production system could use weights, for example, two points per post and one point per vote.

## 2.2 Redis data model

- A Hash `lab1:user:<username>:activity` stores `posts` and `votes`.
- A Set `lab1:user:<username>:voted` records which URLs that user has already voted for.
- A ZSET `lab1:ranking:active_users` stores each username with its total activity score.

The ZSET is the live leaderboard. It is updated when an accepted activity event occurs.

## 2.4 Implement a vote that rejects duplicates

python

```
def vote_for_url(username, url):
    voted_key = f"lab1:user:{username}:voted"
    activity_key = f"lab1:user:{username}:activity"

    # SADD returns 1 for a new member and 0 for a duplicate.
    added = client.sadd(voted_key, url)

    if added == 0:
        return False

    client.hincrby(activity_key, "votes", 1)

    activity = client.hgetall(activity_key)
    posts = int(activity.get("posts", 0))
    votes = int(activity.get("votes", 0))
    score = posts + votes

    client.zadd(leaderboard_key, {username: score})
    return True
```

# Part E — Deliverable 3: Simple recommender system

## 3.1 Design

The goal is to recommend URLs that a user has not selected but that are preferred by other, similar users.

Use:

- A Set for each user's preferred URLs.
- A global Set of users with preference data.
- Jaccard similarity to measure how similar two users are.
- Similarity-weighted candidate scores to rank recommended URLs.

For users $A$ and $B$, define:

$$
J(A,B)=\frac{|A\cap B|}{|A\cup B|}
$$

If both preference Sets are empty, define similarity as zero.

## 3.2 Create preference data

python

```
from collections import defaultdict

USER_INDEX = "lab1:users:with_preferences"

def preference_key(username):
    return f"lab1:user:{username}:preferences"

def set_user_preferences(username, urls):
    key = preference_key(username)
    client.delete(key)

    if urls:
        client.sadd(key, *urls)

    client.sadd(USER_INDEX, username)

demo_preferences = {
    "rec_demo_01": {
        "google.com", "github.com", "python.org"
    },
    "rec_demo_02": {
        "google.com", "github.com", "stackoverflow.com"
    },
    "rec_demo_03": {
        "google.com", "github.com", "youtube.com"
    },
    "rec_demo_04": {
        "nytimes.com", "bbc.com"
    },
    "rec_demo_05": {
        "python.org", "github.com", "stackoverflow.com"
    }
}

for username, urls in demo_preferences.items():
    set_user_preferences(username, urls)
```

## 3.3 Find similar users

python

```
def get_preferences(username):
    return client.smembers(preference_key(username))

def jaccard_similarity(user_a, user_b):
    a = get_preferences(user_a)
    b = get_preferences(user_b)

    union = a | b

    if not union:
        return 0.0

    return len(a & b) / len(union)

def find_similar_users(target_user):
    users = client.smembers(USER_INDEX)
    results = []

    for other_user in users:
        if other_user == target_user:
            continue

        score = jaccard_similarity(target_user, other_user)

        if score > 0:
            results.append((other_user, score))

    return sorted(results, key=lambda item: (-item[1], item[0]))
```

## 3.4 Recommend new URLs

python

```
def recommend_urls(target_user, top_n=5):
    target_preferences = get_preferences(target_user)
    similar_users = find_similar_users(target_user)

    candidate_scores = defaultdict(float)

    for similar_user, similarity in similar_users:
        other_preferences = get_preferences(similar_user)

        # Exclude URLs already preferred by the target user.
        candidates = other_preferences - target_preferences

        for url in candidates:
            candidate_scores[url] += similarity

    return sorted(
        candidate_scores.items(),
        key=lambda item: (-item[1], item[0])
    )[:top_n]
```

## 3.5 Test the recommender

python

```
target = "rec_demo_01"

print("Target preferences:", sorted(get_preferences(target)))

print("\nSimilar users:")
for username, score in find_similar_users(target):
    print(f"{username}: {score:.3f}")

print("\nRecommendations:")
recommendations = recommend_urls(target)

for url, score in recommendations:
    print(f"{url}: score={score:.3f}")

assert all(
    url not in get_preferences(target)
    for url, _ in recommendations
)

similarities = dict(find_similar_users(target))
assert abs(similarities["rec_demo_02"] - 0.5) < 1e-9
assert abs(similarities["rec_demo_03"] - 0.5) < 1e-9

print("\nRecommender verification passed.")
```

### Explanation

The target user shares two URLs with each of `rec_demo_02` and `rec_demo_03`. Each of these users has four URLs in the union of their preferences with the target, so their similarity is $2/4=0.5$.

URLs that the target user has not selected are considered candidates. Each similar user contributes their similarity score to the URLs they prefer. The highest-scoring candidates are recommended first.

This design prevents recommendations of URLs already in the target user's preference Set. Redis Sets are particularly suitable because they automatically eliminate duplicate preferences.

Limitations: This is a basic collaborative filtering system, not a production recommendation engine. It uses only positive preferences, and users with no overlapping preferences receive no recommendations. A real system might provide a fallback to popular URLs, include category similarity, and optimize similarity calculations for a much larger user base.

# Part F — Deliverable 4: Ten most recent websites per user

## 4.1 Design

The assignment requires each user's ten most recent visit events, ordered by time, with the latest visit first.

Use a Redis List named `lab1:user:<username>:visited`.

- `LPUSH` inserts a new visit at index zero.
- `LRANGE key 0 9` retrieves the ten most recent events.
- `LTRIM key 0 9` keeps only the ten most recent events.

A List is suitable here because the assignment asks for recent visit events, and repeated visits must be preserved.

## 4.2 Implementation

python

```
def record_visit(username, url):
    history_key = f"lab1:user:{username}:visited"

    client.lpush(history_key, url)
    client.ltrim(history_key, 0, 9)

def get_recent_visits(username):
    history_key = f"lab1:user:{username}:visited"
    return client.lrange(history_key, 0, 9)
```

## 5.4 Written answers

(a) Why do sessions usually have expiration times?

Sessions often contain authentication or temporary application state. Expiration limits how long abandoned or stale sessions remain valid, reducing security risks and storage consumption.

(b) When might a URL mapping expire?

A mapping may be temporary for a time-limited campaign, invitation, preview, or event link. Permanent links should not receive a TTL unless the application explicitly requires expiration.

(c) Which data should never expire?

Data intended to be durable—such as permanent URL mappings, user records, and required ownership information—should not expire accidentally. Retention must still follow the application's privacy, legal, and deletion policies.

(d) What are the disadvantages of keeping all data indefinitely?

- Storage and backup requirements grow.
- Stale or unused data accumulates.
- Maintenance and operational costs increase.
- Unnecessary retention may create privacy and security risks.

# Part H — Deliverable 6: Atomic counters and concurrent updates

## 6.1 Demonstrate the problem with manual updates

python

```
counter_key = "lab1:counter:concurrency_demo"

client.set(counter_key, 5)

# Simulate two clients reading before either writes.
client_a_value = int(client.get(counter_key))
client_b_value = int(client.get(counter_key))

client_a_new = client_a_value + 1
client_b_new = client_b_value + 1

client.set(counter_key, client_a_new)
client.set(counter_key, client_b_new)

manual_result = int(client.get(counter_key))

print("Manual result:", manual_result)
print("Expected result:", 7)

assert manual_result == 6
```

Both simulated clients read 5 and independently calculate 6. The second write overwrites the first, so the result is 6 rather than 7. This is a lost update.

## 6.2 Demonstrate atomic `INCR`

python

```
client.set(counter_key, 5)

result_a = client.incr(counter_key)
result_b = client.incr(counter_key)

atomic_result = int(client.get(counter_key))

print("First INCR:", result_a)
print("Second INCR:", result_b)
print("Final counter:", atomic_result)

assert result_a == 6
assert result_b == 7
assert atomic_result == 7

print("Atomic counter verification passed.")
```

### Explanation

Redis executes each `INCR` as one atomic server-side operation. Both increments are applied, and the final counter is 7.

The manual example simulates a possible concurrent interleaving; it does not rely on a race condition occurring by chance.

Atomicity applies to the increment itself. If a URL mapping and its counter must always be updated together, use a transaction or Lua script to make the combined operation atomic.
